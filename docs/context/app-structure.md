# App structure

## Layer architecture (§II.4)

Layers are strictly ordered. A layer may import from layers below it, **never
above**.

```
app/            — routes, pages, API handlers (Next.js App Router)
  ↓
components/     — React components
  ↓
services/       — business logic; orchestrates repositories
  ↓
db/repositories/— data access; the only place Drizzle queries live
  ↓
db/schema.ts    — Drizzle table definitions
  ↓
lib/            — pure functions, zero framework imports
```

### Why each boundary exists

- **`lib/` imports nothing framework.** No React, no Next, no database. Pure
  TypeScript over plain data. This is what makes the domain logic (wikilink
  parser, tag parser, slug, title, markdown pipeline, contrast math) fast to test
  and impossible to break by accident. The wikilink parser has no idea a database
  exists. Enforced by convention + review; `lib/**` carries a 100% coverage floor
  precisely because it is cheap to cover.
- **`db/repositories/` is the only place Drizzle queries live.** Repositories
  return **domain types, not Drizzle rows** — the mapping happens at the repository
  boundary so services never couple to the ORM. Swapping the ORM is a
  repository-layer change, nothing above notices.
- **`services/` orchestrates repositories** and holds multi-step business logic
  (the PATCH cascade, import's two-pass resolution, export assembly). A service may
  call several repositories inside one transaction; a repository never calls a
  service.
- **`components/` and `app/`** are the only layers that touch React/Next. `app/`
  routes are thin: validate input (zod) → call a service → shape a response.

The theme system lives in `themes/` (a sibling of `lib/`), consumed by
`components/` and `app/`. Theme definitions are pure data (no framework imports),
so they sit at the same purity level as `lib/`.

## Data model (§II.2)

Postgres via Neon (pooled HTTP connection), Drizzle ORM. Schema in `db/schema.ts`;
migrations generated by Drizzle Kit and committed.

### Tables

- **`notes`** — `id`, `title` (derived), `slug` (stable), `body` (raw md),
  `is_daily`, `daily_date`, timestamps, `deleted_at` (soft delete), and a stored
  `search_vector` tsvector (title weight A, body weight B).
- **`tags`** — `id`, `name` (full path, unique), `parent_id` (self-ref, cascade),
  `created_at`. The hierarchy is materialised: `books/fiction/calvino` → three
  rows, parent-chained.
- **`note_tags`** — join, PK `(note_id, tag_id)`. A note links to the **leaf tag
  only**.
- **`links`** — resolved note→note, PK `(source_id, target_id)`.
- **`unresolved_links`** — `(source_id, target_slug)`, wikilinks to notes that
  don't exist yet.
- **`assets`** — uploaded files; tracks `blob_url`, `pathname`, `filename`,
  `mime_type`, `size_bytes`, optional `note_id`.

### Indexes

GIN on `notes.search_vector`. B-tree on `notes.deleted_at`, `tags.name`,
`tags.parent_id`, `links.target_id`, `unresolved_links.target_slug`,
`note_tags.tag_id`, `assets.note_id`.

### Constraints (these are tested, not decorative)

- `CHECK ((is_daily=false AND daily_date IS NULL) OR (is_daily=true AND daily_date IS NOT NULL))`.
- **Partial unique** on `daily_date WHERE deleted_at IS NULL` — one live daily note per date.
- **Partial unique** on `slug WHERE deleted_at IS NULL` — soft-deleted notes don't squat on a slug.

The partial uniques are why `slug` and `daily_date` carry no inline `unique`: a
plain unique would let a trashed note block slug reuse forever.

### Tag hierarchy rule

Ancestors are materialised as `tags` rows but **not** denormalised into
`note_tags`. A note tagged with a leaf gets one `note_tags` row (the leaf).
Ancestor rollup happens at query time via a recursive CTE. Denormalising ancestors
would create a second source of truth that drifts.

## The PATCH cascade (§II.7)

The most complex operation, isolated in `services/note-sync.ts`, all in **one
transaction**:

1. Update `body`, re-derive `title`.
2. Re-parse tags → diff vs current `note_tags` → insert new tags + ancestors, link
   leaf, unlink removed.
3. GC tags with no notes **and** no tagged descendants.
4. Re-parse wikilinks → resolve slugs → replace `links` / `unresolved_links` for
   this source.
5. **Link healing**: any note whose slug now matches a previously-unresolved link
   gets those links promoted from `unresolved_links` to `links`.

## Environment boundaries (mocked in this build)

Two external services require credentials the build does not have:

- **Neon Postgres** — integration/repository tests run against **pglite**
  (in-process Postgres), not real Neon. Same SQL dialect. See `conventions.md`.
- **Vercel Blob** — asset upload/delete is written against a **mockable blob
  gateway** (`lib/blob` interface) so services and routes are testable without a
  real token. The real adapter calls `@vercel/blob`; tests inject an in-memory
  adapter.

These boundaries, and everything owed to the architect's real deployment, are
listed in the final report's `NOT DONE` / `OWED VERIFICATION`.
